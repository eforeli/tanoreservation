# TANO 訂位系統｜系統架構與資料庫初稿
版本 v1.4 — 2026-11-14

## 1. 架構
```
LINE 官方帳號「我要預約」
       |
       v
公開訂位前台 /reserve  -----> Next.js Server Actions/API
                                     |
管理員 /admin -- Supabase Auth ------+
                                     |
                              Booking Service
                    (時段查詢／分桌／加椅／鎖桌)
                                     |
                             PostgreSQL (Supabase)
                                     |
                               RLS + audit log

部署：Vercel（前後台可在同一個 Next.js 專案）
```

建議技術：Next.js + TypeScript、Supabase Postgres + Supabase Auth、Vercel。前台／後台共用一份業務邏輯，後台使用有驗證的路由；公開訂位由伺服器端 API 控制，不將資料庫的寫入權限放到瀏覽器。

## 2. 資料表初稿
- `restaurant_tables`: `id`, `code` (`A1`–`A5`), `base_capacity`, `max_capacity`, `is_active`, `sort_order`, `created_at`。
- `reservations`: `id`, `confirmation_code`, `guest_name`, `guest_phone`, `party_size`, `starts_at`, `dining_ends_at`, `table_released_at`, `status`, `notes`, `source`, `created_at`, `updated_at`, `cancelled_at`, `cancel_reason`。
- `reservation_tables`: `reservation_id`, `table_id`（第一版每筆僅 1 桌，保留將來併桌擴充性）。
- `table_blocks`: `id`, `table_id`, `start_at`, `end_at NULL`, `reason`, `created_by`, `created_at`, `released_at`；NULL 結束代表持續鎖定。
- `weekly_business_hours`: `weekday`, `opens_at`, `closes_at`, `is_closed`。
- `special_business_hours`: `id`, `business_date`, `opens_at NULL`, `closes_at NULL`, `is_closed`, `notes`。
- `booking_settings`: `dining_minutes`, `buffer_minutes`, `slot_interval_minutes`, `booking_window_days`, `min_advance_minutes`, `extra_chairs_total`, `max_arrivals_per_slot`, `max_online_party_size`, `last_seating_rule`。
- `admin_audit_logs`: `id`, `actor_user_id`, `action`, `entity_type`, `entity_id`, `old_value`, `new_value`, `created_at`。

**實作注意：** 過去日期與狀態變更不可導致個資遺失；桌位編號應是唯一 key。資料庫時間統一儲存為 `timestamptz`；時段運算時以餐廳時區推導營業日。

## 3. 椅子資源建模
目前標準座位 14、共享額外椅 2。每張桌最多 1 張加椅。

一筆分配到某桌的訂位所需椅數：`max(0, party_size - base_capacity)`，且 `party_size <= max_capacity`。

所有同時有效訂位在重疊椅子占用時段內，額外椅總需求不得超過 `booking_settings.extra_chairs_total`。

**避免出錯：** 不只計算請求起點的可用椅子；需在新訂位占用區間所有重疊事件起訖點檢查峰值需求。

## 4. 防止併發超賣
不可採前端查詢後直接插入的非原子流程。可透過 PostgreSQL transaction 搭配每餐廳／營業日的 advisory lock、行鎖或容量資源鎖，將「讀取占用 → 選桌 → 椅子容量檢查 → 新增訂位」包入同一交易。

資料庫還應建立必要索引、去重 token（idempotency key）與狀態管理；對同桌重疊可用 `tstzrange` + 排除約束或等效交易驗證，必須排除 cancelled 等非占用狀態，並對鎖桌衝突做額外檢查。

## 5. 預計 API
- `GET /api/availability?date=YYYY-MM-DD&partySize=N`：返回合法入席時段（不暴露客人資料／內部分配桌號）。
- `POST /api/reservations`：建立訂位，驗證資料、限流、idempotency、交易分配。
- `GET /api/admin/reservations`：授權管理員查詢。
- `POST /api/admin/reservations`：管理員新增電話／現場訂位。
- `PATCH /api/admin/reservations/{id}`：修改、重分配；交易中先驗證再提交。
- `POST /api/admin/reservations/{id}/cancel`：取消、釋出庫存、寫入 audit。
- `POST /api/admin/table-blocks`：鎖桌、註記原因並列出衝突。
- `PATCH /api/admin/table-blocks/{id}`：修改鎖定或解除。
- `GET /api/admin/occupancy?date=...`：桌位時間軸。
- `PATCH /api/admin/settings`：更新限制與營業設定。

## 6. 權限與資安
公開 API 應走受控 server endpoint；不得使用 public anon key 直接 SELECT 全部 `reservations`。管理端以 Supabase Auth 登入，所有 API 在 server 端驗證管理身分；RLS 作第二道防線。service role key 僅能放伺服器環境變數，不可暴露到 client。所有管理變更寫入 audit logs。依台灣個資法需求規劃資料告知、存取與保存期限。

## 7. 部署
開發 → staging（假資料測試）→ production。Vercel 放站台與 API；Supabase 放資料庫與 Auth。設定獨立環境變數及資料庫遷移。可沿用 TANO 現有網站網域規劃 `/reserve`、`/admin`，但需檢查現有框架和路由架構再定整合方式。
